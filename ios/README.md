# MindMap for iOS

The native counterpart to the React app in this repo. Same product, same
vocabulary, same scorer: the Swift network in `Scoring/` runs the weights the
web app runs, and the unit tests check it against the web app's own answers.

MindMap measures physiology and reports patterns. It is not a medical device
and does not diagnose or treat any condition.

## Which route this took, and why

**There is no checked-in `project.pbxproj`.** These sources are a Swift
package, and the Xcode project is created once on your Mac from the steps
below.

A hand-written `project.pbxproj` for an app target plus a unit test target
plus a bundled resource cannot be verified without running Xcode, and a
corrupt one is worse than none: it fails at open with no useful message and
the usual fix is to delete it and start again. A package manifest can be
verified, and was. `swift build` and `swift test` are green on this tree.

What you get instead:

* a two module package that Xcode adds to the app target in one step;
* `swift test` on the Mac with no project, no scheme and no simulator, which
  is how the scorer parity tests are meant to be run;
* a five minute setup, below.

## Making the Xcode project

Five steps. Nothing is typed twice and nothing is dragged twice.

1. **New project.** Xcode, File > New > Project > iOS > App. Next.
2. **Fill the sheet.**
   * Product Name: `MindMap`
   * Organization Identifier: `com.solaceinnovation`
   * Interface: **SwiftUI**
   * Language: **Swift**
   * Storage: **None**
   * Testing System: **None** (the tests live in the package)
   * Leave Core Data and CloudKit off.

   That gives bundle identifier `com.solaceinnovation.mindmap`. **It is a
   placeholder and has to be registered** on an Apple Developer account
   before the app can be installed on a device or submitted. Nobody has
   registered it yet. Change it if it is taken, and change it in nothing else:
   no other file in this tree names it.

   Save it somewhere **outside this repo**, or add its folder to `.gitignore`.
   The generated project is machine specific and does not belong in version
   control.
3. **Delete the stub.** In the new project, delete `ContentView.swift` and the
   generated `MindMapApp.swift`, moving both to Trash.
4. **Add the package.** File > Add Package Dependencies, then the **Add Local**
   button at the bottom of the sheet, and choose this `ios` folder. When Xcode
   asks which products to add to the `MindMap` target, tick **MindMapKit** and
   **MindMapUI**.
5. **Add the app file and the purpose strings.**
   * Drag `ios/MindMap/App/MindMapApp.swift` into the project, ticking
     "Copy items if needed" off and adding it to the `MindMap` target.
   * Open the `MindMap` target > Info and add the three keys from
     `ios/MindMap/App/Info.plist`: `NSBluetoothAlwaysUsageDescription`,
     `NSCameraUsageDescription`, `NSMicrophoneUsageDescription`. Copy the
     strings across verbatim. Alternatively set the target's Build Setting
     `INFOPLIST_FILE` to that file.
   * Do **not** add a Background Modes capability. This build does not read
     the patch in the background and `bluetooth-central` must not be
     declared until it does.

Build and run. Nothing else needs a capability: there is no account, no
network, no push, no HealthKit and no App Group.

If `import MindMapUI` fails to resolve, step 4 did not take: check the target's
General > Frameworks, Libraries and Embedded Content for both libraries.

## Running the tests

From a terminal, with no Xcode project at all:

```
cd ios
swift test
```

Forty six tests. The one that matters most is
`ScorerParityTests.testScoreMatchesTheJavaScriptScorerWithinOnePoint`, which
runs 1000 z-score inputs through the Swift network and compares every answer
to the web app's. Measured on this tree: **every one of the 1000 agreed
exactly, and the largest difference in the underlying probability was
2.2e-16**, which is one unit in the last place of a double. The test allows a
gap of one score point and 1e-9 in the probability, so there is a wide margin
before a real divergence would be missed.

The fixture records the probability at full double precision on purpose.
Rounding it would put a floor under that measurement larger than the thing
being measured.

The package lists macOS as a platform for this reason only. Every file that
needs UIKit or an iOS-only SwiftUI modifier is behind `#if os(iOS)`, so a host
build compiles what the tests exercise and skips the screens. In Xcode the
same tests run against the iOS simulator with no change.

## Regenerating the weights and the fixture

Both are generated. Never edit either by hand.

```
python3 tools/net/train.py        # refits, rewrites src/signals/net-weights.js
node ios/tools/gen-weights.mjs        # copies those numbers into net-weights.json
node ios/tools/gen-parity-fixture.mjs # re-records the JS scorer's answers
cd ios && swift test                  # confirms the Swift port still agrees
```

`gen-weights.mjs` imports the JavaScript module and serialises what it holds,
so no number is ever retyped. The network is 261 parameters, architecture
4-16-10-1, fitted to the published-coefficient reference model documented in
`tools/net/train.py`. It is not fitted to anybody's readings, and
`ScorerParityTests` asserts both the architecture and the parameter count so a
weights file from a different model cannot be dropped in unnoticed.

## What the patch UUIDs are

`PatchIdentifiers.swift` holds every identifier the app uses, and they are
placeholders. The service and characteristic UUIDs are the Nordic UART
Service, which is what the current firmware sketch advertises and what the web
app pairs against in `src/lib/engine.js`. When the firmware is final:

1. replace the three UUIDs in that one file;
2. check `PatchFrame.byteCount` and the four scale factors against the packed
   struct the firmware writes;
3. run `swift test`, because `PatchFrameTests` pins the decode to the encode.

Nothing else in the project names a UUID or a byte offset.

The frame format in `PatchFrame.swift` is also a placeholder: twelve bytes,
little endian, a sample counter and four signed fixed point channels. It is
documented in that file and nowhere else.

## What is ported and what is not

Ported and working:

* the Mind Score network and the reference model it was fitted to;
* the Welford baseline, including the rule that under five captures a personal
  spread is mostly noise and the prior's spread is used instead;
* the four bands and the sentence that goes above the number;
* the six question route;
* the consent model, as types;
* the patch route end to end, over Bluetooth Low Energy or the simulated
  patch;
* Paced breathing, Feeling map and Senses count from the toolkit.

**Not ported.** The camera and microphone route. The web app extracts a pulse
from the camera and pitch features from the microphone in `src/signals/ppg.js`
and `src/signals/voice.js`, and that signal processing has not been written in
Swift. `Baseline.phoneCapturePriors` is already carried over for it, so the
work is the feature extraction and nothing else.

That has one consequence worth being deliberate about: the camera and
microphone purpose strings in `Info.plist` describe a route this build does not
yet take. **Either ship that route or delete those two keys before
submitting.** Declaring a permission the app never asks for is a metadata
problem in review, not a harmless extra. See `docs/app-store.md`.

Also not ported: Absolute words and The pile from the toolkit, and the parent
and medical professional dashboards, which are separate surfaces in the web
app rather than screens of the student app.

## The rules this code is written to

These are product rules, and several are enforced by the types rather than by
review. Changing one is a decision, not a refactor.

* **Nothing leaves the device without an explicit grant.** There is no network
  client in the app. `SharePayload` has no public initialiser: the only way to
  make one is `SharePayloadBuilder`, which needs an active `ConsentGrant`.
* **A parent sees nothing finer than a day.** `Audience.parent.ceiling` is
  `.day` and `ConsentGrant.init` floors every grant by the audience ceiling,
  so a grant cannot ask for more.
* **Notes, location and anything said are never shared.** `JournalNote`,
  `LocationFix` and `MicrophoneSession` conform to `NeverShared` and not to
  `Shareable`, so `builder.add(note)` does not compile. There is no runtime
  path to try.
* **A medical professional sees only what was consented to.** No category is
  implied by another and no grant covers everything.
* **No claim the product cannot carry.** No unit has been built or worn. There
  is no clinical trial, no validation study and no diagnosis. The one sentence
  in `Vocabulary.notAMedicalDevice` is required on any screen that shows a
  score.
* **Nothing nags.** No streaks, no badge counts, no reminders that imply a
  missed day is a failure, and no screen that puts one student next to
  another.
* **Nothing asks for discomfort.** Every toolkit step is either noticing what
  is already there or slowing a breath down.
* **One name per thing.** `Vocabulary` is the single source for product words,
  the same rule `src/lib/terms.js` sets for the web app.
